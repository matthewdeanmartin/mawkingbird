# What the web client’s comments leave unfinished

Reviewed 2026-11-21 against commit `7457bd021`. **Pending-account setup is the clearest case where a developer could read a comment, believe a feature is done, and move on.** A second case, moving a Misskey bookmark to Raindrop, shows how a rule documented in one branch was missed in another.

I found no comment telling a developer to finish an implementation because it was too hard. The closest literal match was a quotation about avoiding dozens of unnecessary bookmark requests. The surrounding method explains when it makes the request and how the answer is cached. The comments establish what the code promises. They do not establish who wrote it. [Home bookmark probe](../ui/src/app/feeds/home/home.ts#L2090)

## Two behaviors worth investigating first

### 1. Pending Mastodon setup promises to save changes it can reject

The setup state says steps that would write to the server save locally while approval is pending. The setup screen tells the person they can continue. The intro step really can save a draft. The profile step, however, sends the changed name, bio, or avatar straight to `updateCredentials`. When that fails, Next offers retry or skip. The discoverability step also writes to the server when settings are available. The stored setup record has fields for progress and answers, with no place to keep either set of pending edits. [State comment](../ui/src/app/accounts/setup/setup-state.ts#L57) · [User-facing notice](../ui/src/app/accounts/setup/account-setup.html#L21) · [Intro draft](../ui/src/app/accounts/setup/steps/setup-intro.ts#L74) · [Profile save](../ui/src/app/accounts/setup/steps/setup-profile.ts#L81) · [Discoverability save](../ui/src/app/accounts/setup/steps/setup-findable.ts#L91) · [Error on Next](../ui/src/app/accounts/setup/account-setup.ts#L118) · [Stored fields](../ui/src/app/accounts/setup/setup-store.ts#L32)

The storage comment calls the queue future work. The feature plan goes further and describes resuming after approval, applying queued changes, and expiring them after 30 days. I found no corresponding approval replay route. I would settle the product promise first. If pending setup should survive, the acceptance case is a pending account editing its bio, closing the browser, and returning after approval to apply that edit once. If intro drafts are the intended limit, say exactly which step can save progress. The code also treats every verification 403 as pending, which its own comment flags as an unverified assumption. [Storage comment](../ui/src/app/accounts/setup/setup-store.ts#L11) · [Planned approval flow](new-account-setup.md#L252)

### 2. Misskey bookmarks are local when listed and remote when moved

The Bookmarks comment accurately says a Misskey account’s bookmarks live in the browser. Both initial load and pagination read the local store. With Raindrop connected, the page offers a Move button. That handler adds the destination bookmark first. It removes the local source only for an anonymous identity. A Misskey post falls through to the Mastodon unbookmark call. If removal fails, the user can see a failed move after the destination copy already exists. Even if the call succeeds, that branch never removes the source from local storage. This is a source-level finding. I did not exercise a live account. [Local reads](../ui/src/app/reading/bookmarks/bookmarks.ts#L183) · [Move button](../ui/src/app/reading/bookmarks/bookmarks.html#L109) · [Move handler](../ui/src/app/reading/bookmarks/bookmarks.ts#L277) · [Anonymous identity check](../ui/src/app/platform/session/auth.ts#L549)

I would keep the local-storage comment and use it as a regression case. Move a local Misskey bookmark with Raindrop connected, reload, and verify one destination copy, no local copy, and zero Mastodon unbookmark requests.

## Low-value prose and comments worth keeping

- “That is the difference between publishing and littering” adds a judgment to the paste provider. The nearby explanation of per-paste versus per-account authority earns its space. It tells a maintainer why wiring Edit and Delete to the shortener could grant the wrong authority. [Paste provider](../ui/src/app/connections/paste/shortener-paste-provider.ts#L42)
- “The app does not lecture people about what they paste” adds nothing to the feed sync contract. A sentence identifying which data leaves the device would help someone decide whether changing the sync path is safe. [Feed sync](../ui/src/app/accounts/mawkingbird/profile-feeds.ts#L25)
- I would keep the article reader’s note about a possible shared failure database. Today the history stays local and can be exported. The comment identifies consent as a new decision before any automatic collection. Counting that as an overdue implementation would misread the design. [Observed failures](../ui/src/app/reading/article/observed-failures.ts#L23)

## Review boundary

This was a read-only source audit of the maintained web client. I searched production code, templates, library code, tests and UI scripts for explicit deferrals, softer roadmap wording, stubs, and refusal language, then followed candidates into callers, persistence, tests and feature plans. Generated copy, fixture TODOs, translation keys and Angular deferred loading produce many false positives. I used the committed snapshot as the reference so another developer’s in-progress changes would not be mistaken for shipped behavior. This is a set of verified findings from a targeted search, rather than a line-by-line certification of every comment. No runtime tests were run for this document.
