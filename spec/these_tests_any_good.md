# Are these tests any good?

Static review, 17 November 2026. Start with the feed aggregator’s deadline test and Native article response limits. Both cover behavior worth protecting, and both would stay green under a plausible regression. The clearest pure duplicate is in Hugo settings. There are also tests worth copying, especially the admin form retry scenarios.

I searched the working tree for conditional assertions, weak bounds and fixed browser waits, and compared literal callback bodies across the 836 tracked TypeScript spec files. I read selected cases in context, including distinct guard suites with identical-looking tests, the client integration suite, browser checks, and Native Rust tests. This is a targeted sample anchored at HEAD `57c0a521d` in a shared checkout. The findings describe specific cases. They do not estimate a suite-wide defect rate. No suites, builds, benchmarks or coverage collection ran.

## Fix first

1. **A feed source can disappear and still satisfy the deadline test.** In [feed-aggregator.spec.ts](../ui/src/app/feeds/feed-aggregator.spec.ts), “bounds a slow source across its own paging” schedules one distinct post every six simulated seconds. It awaits the page, discards it, and accepts any call count up to two, including zero. Skipping this source entirely or throwing away the first page at timeout satisfies that assertion. The [production recursion](../ui/src/app/feeds/feed-aggregator.ts) promises to retain collected posts. Assert that the result contains exactly `r1`, that the second request started and that the round settled at the shared deadline. Keep the fake clock. Advancing it sixty seconds before inspecting completion hides a late return.

2. **The Native response-size test covers only the declared-length path.** In [articles.rs](../native/src-tauri/src/articles.rs), `response_limits_and_status_survive_real_http_transport` serves an empty body with an oversized Content-Length. That exercises the early rejection in `read`. Removing the cumulative byte check inside the chunk loop would still satisfy it. Keep that inexpensive header case and add a localhost response with no Content-Length, delivering more than the limit across multiple writes. Assert the specific `too-large` result. The separate character-decoding test covers expansion after decoding, a third failure point.

3. **Random selection makes a failure assertion optional.** In [feed-flooding.spec.ts](../ui/src/app/feeds/feed-builder/feed-flooding.spec.ts), “reads at most a fixed number of hashtags” supplies twelve tags, lets [checkTags](../ui/src/app/feeds/feed-builder/feed-flooding-check.ts) shuffle and choose eight, then throws only for `t3`. On runs that omit it, the guarded assertion never executes. Make the first selected read reject, record its tag, then require a matching empty reading and successful sibling readings. The same case claims “40 posts each” but compares every request to the production constant. Changing that constant to 400 keeps the test green. Use the literal limit if 40 is the promised request budget.

4. **The flooding threshold case misses its named boundary.** In the same spec, “at a quarter or more” supplies eligible leaders at 30% and 27.5%, plus an undersized sample. Changing the share comparison from inclusive to exclusive leaves those results intact. Use eight posts with four authors contributing two each for exactly 25%, and an eligible sample with five authors contributing equally for below 25%. Check the number of flagged accounts so the test is independent of tie-breaking.

## Duplicates, claims and mocks

- **One confirmed duplicate.** In [hugo-settings.spec.ts](../ui/src/app/connections/hugo/hugo-settings.spec.ts) lines 34 and 52, both cases inject the same service after the same storage reset, connect the same repo and token, and assert the identical default feed URL. Give the second case a different history: set a discovered URL, clear it with `setFeedUrl(null)`, then require the derived URL again. That covers a transition with the existing test slot. By comparison, “allows authenticated accounts through” appears twice in [anonymous-route.guard.spec.ts](../ui/src/app/accounts/anonymous/anonymous-route.guard.spec.ts), but the local runners invoke different guards. Both can regress independently.
- **An export name promises more than the application does.** The [app OPML spec](../ui/src/app/reading/rss/opml.spec.ts) says successive exports avoid overwriting one another. It checks one timestamp. The [formatter](../ui/src/app/reading/rss/opml.ts) emits a UTC date, so two exports the same day have identical suggested names. Name the case for the dated filename. A pair of instants straddling UTC midnight would verify the date rule precisely. File collision handling would require a separate product decision.
- **A permissive mock hides provider mapping mistakes.** In [native-account-publishing.spec.ts](../ui/src/app/connections/native-account-publishing.spec.ts), “routes every account-backed shortener create” passes each adapter one response containing competing field names such as `originalURL`, `long_url` and `destination`, all set to the same URL. A provider could read a sibling provider’s field and still pass. The observed POST, provider ID, handle and absence of plaintext are genuine client behavior. Keep those assertions and use a minimal response per provider if this case is also meant to validate parsing. Its fake global invoke discards the command name. The separate [Native platform spec](../ui/src/app/platform/http/platform-http.native.spec.ts) is where exact bridge command assertions already live.
- **API coverage has a clear UI boundary.** “Keeps hashtag follows stateful across the controls used by bundles and search” in [the Mastodon integration suite](../ui/integration/mastodon-api.integration.ts) calls API methods directly. A disconnected button would leave it green. Name it for the API round trip. The post lifecycle case in that file is a good model: it edits through the client, reads back the changed content in a second request, deletes, and checks for 404. That makes the installed mock server a meaningful collaborator.

## Cost and organization

- **Replace elapsed waits with evidence of arrival.** The starter-kit and Fantascienza navigation checks in [check-seo-browser.mjs](../ui/scripts/check-seo-browser.mjs) wait for the exact URL, sleep 500 ms, then reread the pathname. A blank destination could still pass. Wait for a stable destination control or heading and check the URL there, preserving the existing runtime-error collection. The preview navigation a few lines later already waits for its heading. The hover delay in [feed-refinements.browser.mjs](../design_system/tests/feed-refinements.browser.mjs) has a different purpose: the popup must survive a pending dismissal. Preserve that observation window if switching it to a controlled clock. These are source-level opportunities, with no measured timing or savings.
- **Put tests where someone changing the feature will find them.** The last two cases in the flooding spec exercise YouTube subscription buttons and real subscription state. Keep the tests, but place their describe block beside `youtube-subscribe.ts` when next editing that feature. Similarly, the browser file named “feed refinements” opens with report typography and help popovers. Group future browser cases by the user-visible feature, keeping story IDs and screenshot names stable. Preserve the protected inventories when undertaking any move.
- **Keep divisions that carry different evidence.** The [library OPML spec](../ui/src/lib/rss/opml.spec.ts) owns XML parsing and nested folder paths. The app wrapper owns the branded title, disabled-subscription export and filename. The [admin form adoption spec](../ui/src/app/admin/admin-form-adoption.spec.ts) also earns its table of similar-looking cases. Each row mounts a different real form, drives native input, observes the outgoing payload, rejects it with 422, then retries and checks retained and cleared input. A broken binding in one component can fail just that row.

The smallest useful first pass is to strengthen the two feed specs, give the duplicate Hugo case its own state transition, and cover the Native streaming limit. Each change has a specific regression it should catch. File moves and browser timing work can proceed separately.

## Handoff for a stricter testing strategy

Keep the existing named tests and protected inventories. Upgrade assertions in place and add a named scenario when it protects a distinct failure. The current [integrity check](../ui/scripts/check-test-integrity.mjs) catches literal always-true assertions and enforces declaration floors. A green count can coexist with a conditional assertion that never ran. Track one additional piece of evidence for each pilot below: the specific wrong implementation the scenario catches.

| Method and current evidence | First pilot and acceptance criterion |
| --- | --- |
| **Targeted mutation testing.** No Stryker or cargo-mutants wiring surfaced in the inspected manifests or workflows. | Once a developer has an isolated checkout, temporarily change the flooding comparison to exclude exactly 25%, then separately discard collected posts at the feed deadline. Run only the corresponding spec for each. Record the named failure, restore the source and confirm the same spec passes. A compile failure is inconclusive. Start with these two plausible mistakes before proposing tooling or a score threshold. |
| **Property-based testing.** The library already has hand-picked round trips and permutation examples. No fast-check, proptest or quickcheck dependency surfaced in the inspected manifests. | Extend the [OPML library tests](../ui/src/lib/rss/opml.spec.ts) with generated valid subscriptions containing Unicode labels, XML metacharacters and nested folders. Use unique canonical HTTPS URLs initially. After export and import, compare the URL, title and folder sequence to the input. Keep the independently authored XML fixtures to catch mutually compensating parser and writer mistakes. Keep a reproducible seed and save the smallest failing example. |
| **Model-based sequence testing.** The queue already tests add, undo, partial publish and reload as examples. | In [PosseQueue](../ui/src/app/connections/hugo/posse-queue.spec.ts), keep a tiny independent list of expected action-kind/URL pairs. Start with like A, repost A, like B, publish only the first entry, reload, undo like B. Compare the complete remaining membership after each step. Repost A alone should survive. Once that trace is sound, vary action order, duplicate adds and reload points with a recorded seed. |
| **Fault injection through recovery.** Several layers already inject failures. The remaining opportunity is following the user beyond the first error screen. | Extend one existing deep-link browser case as above. At service level, use the translation second-note check. For a write whose response is lost, first establish whether retry is safe. Where it is unsafe, the existing [Native publishing test](../ui/src/app/connections/native-account-publishing.spec.ts) rightly requires a single outgoing POST. Preserve that guarantee. |
| **Provider contract fixtures.** The Native shortener exercise shares a response containing many providers’ aliases. | Give each provider a minimal, documented or sanitized provider-specific response. Assert the outgoing destination and returned short URL using deliberately different values. Choosing another provider’s response field should fail the affected row. Keep the existing handle and credential assertions. This can use the existing runner and requires no live accounts. |

**Suggested order for the next developer.** Start with the feed deadline assertion, exact flooding boundary and replacement Hugo transition. Then pick one recovery journey and one generative pilot. For each, record the existing case extended, the concrete failure it now detects, and the lowest-cost suite that exercises it. Use the repository’s existing focused-check and gate cadence when implementation is authorized. These notes do not introduce a CI gate. Leave mutation experiments for an isolated checkout. All proposals in this section are pending.

**Owner decisions that affect the next pass**

1. Which failure deserves the first complete user journey: losing writing, losing part of Home, or reaching a dead end from a shared link? A recent real incident would make a good starting fixture.
2. Should the first strictness pilot stay within Vitest using a few hand-selected mutations and deterministic cases, or is a dev-only property-testing dependency acceptable for reproducible generation and shrinking?
3. For the first pilot, is a maintainer-run result enough, or should a successful pilot lead to an optional scheduled check? A decision about CI can wait until the pilot shows which regressions it catches.

## Implementation log, 17 November 2026

- [x] Sprint 1, post edit preservation. The poll lifecycle spec now pins the time of each edit and requires 7,200 then 5,400 seconds on the actual HTTP writes. Previously its expectation called the same production helper as the editor, and its fixed date was already past. The expired fixture separately requires the 300-second minimum sent by the editor. Component HTTP coverage establishes the edit payload. Actual server vote handling is outside this case.

- [x] Sprint 2, cross-post preflight and retry. Extended the existing two-destination metadata test to reject the description write, verify visible feedback and preserved text, forbid either publication, retry the original description, and verify the Fedi media ID and eventual draft clearing. Existing partial-success tests separately cover resuming only the failed network. Preflight can prevent a known bad prerequisite. Each independent network write can still fail after preflight.
- [x] Sprint 3, reading break. A Home component test clicks Load more below a 25-post maximum, supplies another full page, then requires 25 rendered cards and the visible stop in place of paging. Home defaults to 500 stored posts per sitting and a one-hour cooldown. This counter does not accumulate a day's reading across visits. A separate issue surfaced by inspection: the existing override test accepts zero paging requests, and `loadMore()` returns at the maximum even with the override enabled. Whether to rotate held rows to permit continued paging while respecting the memory cap needs a product decision.
- [x] Sprint 4, bounded mutation pilot. Added eligible samples at exactly 25% and just below the rule (20%). Fixed the shuffle input so the error path always runs and the empty reading is mandatory. In a temporary source copy, changing the rejection from `share < FLOOD_SHARE` to `share <= FLOOD_SHARE` failed the new assertion at exactly 25%. The other six cases passed. The runner reported 10.6 seconds to build and 2.2 seconds to run that file on the successful mutation experiment. Those figures describe one narrowed run. No mutation package or recurring gate was added. To reproduce, take a disposable copy including the UI and design tokens, make that one comparison change, and run `npm run test:subset -- src/app/feeds/feed-builder/feed-flooding.spec.ts` in its UI directory.

## Next strategy decisions

**Reading-break decision.** Manual continuation uses a bounded rolling window. At a 20-post cap, if the next response repeats the last post and adds two older posts, Home evicts the first two held rows, retains the other eighteen and shows both new ones. The strengthened test clicks the rendered button, requires the next cursor and checks the exact retained IDs and visible new text. Automatic filling remains bounded. [Home implementation](../ui/src/app/feeds/home/home.ts) · [Home specs](../ui/src/app/feeds/home/home.spec.ts)

**Solo-maintainer workflow.** Use ordinary named cases with a concrete failure and observable result. The owner declined formal BDD and snapshot testing. Keep assertions small enough to review. Generated design inventories already required by the repository have their own review process.

**First browser/server journey.** The [integration launcher](../ui/integration/run.py) already boots the pinned PyPI Mastodon mock, and the [integration spec](../ui/integration/mastodon-api.integration.ts) already reads back posts after writes. Extend this infrastructure with a browser scenario against the built client. Seed an authored post with a warning, sensitivity, two ordered images and distinct alt text. Change only the caption through the edit dialog. Reload the post and compare an independent API read to the seeded fields and new caption. Assert the same ID and one post. This spans the dialog, serializer, server storage and reload. Confirm the wheel models each field before treating it as an oracle.

**Second journey, ambiguous delivery.** Use a disposable Bluesky record store keyed by repo, collection and record key alongside the existing Mastodon fixture. Store the first Bluesky write, then drop its response once. Let the reader retry. Check user feedback, attempted keys, final record count on both servers and the saved text. Include a separate case where the first attempt really was rejected before storage. A scripted sequence of 503 then 200 responses alone cannot reveal duplicate writes. Keep fixtures at the protocol boundary and reset them between cases. The ledger must report what was stored independently of what the UI reports.

**Bounded logic.** The repo already has seven independently checked libraries. For an immediate bounded problem, isolate the cross-post retry decision as a pure app module: given a draft revision, per-network acknowledgements, pending writes and an event, return the next permitted writes and whether the editor may clear. The composer still owns HTTP, signals and presentation. Enumerate both response orders, failed first/last segment, duplicate submit and edits between attempts. Assert that acknowledged segments remain acknowledged and completion clears only the matching revision. This can be exhaustively checked for a small declared model, such as two networks and at most two segments. It still needs a component test for event wiring and a server test for remote persistence. Post editing already has a pure [payload builder](../ui/src/app/publishing/status-edit/status-edit.ts). Exercise its combinations in plain tests before moving code. Promote logic to a standalone library when its inputs and rules make sense outside Mawkingbird and meet the [existing library boundaries](../ops/engineering/libraries.md).
